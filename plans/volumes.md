# One core for the four volumes

Status: phases 0 and 1 done; phase 2 going (the fields' tables and the
voices done for all four). Written 2026-09-26.

The port should boot any of the four discs with one build:

- .hack//Infection (INF)
- .hack//Mutation (MUT)
- .hack//Outbreak (OUT)
- .hack//Quarantine (QUA)

The disc says which volume it is, and the port picks that volume's data
and, where the game's code changed, its code path.

At run time the port reads the disc's data files: `DATA/DATA.BIN`, the
four overlays (`DATA/*.PRG`), `DATA/KFED.BIN` and `KFAED.BIN` on QUA,
`STREAM`, `PSS` and the voices. It never reads the boot executable
(`SLUS_*`). Everything the port takes from the executable today is
generated into the source, per volume, as typed data.

## Where we are

**Infection only.** Every reader assumes `SLUS_202.67` and Infection's
addresses:

- 27 source files open the executable (a few only in their tests). They
  read the event scripts and messages (`piney_event::official`), the area
  words (`piney_data::area`), the save's initial strings, the stream
  tables, the desktop's, title's and top page's assets, the field UI's
  texts, and the battle's tables (skills, items, enemies, the navigator,
  Kite, the members, the entries).
- About 540 `const ...: u32` addresses in 80 files point into Infection's
  main section, its overlays and its heap. The largest sets are the
  party's chat (81), the field UI's tables (57), the items (25), the
  battle's tables (22) and name entry (18).
- `ELF_PATH = "SLUS_202.67"` is declared in three crates.

**Already per-volume in shape.** Four systems read generated tables, not
the executable:

- the dungeons (`piney_data::dungeon::inf`, then `tools/dungeon_tables.py`; now `placement::dungeon`);
- the fields (`field::inf`, then `tools/field_tables.py`; now `placement::field`);
- the sound (`sound::inf`, then `tools/sound_tables.py`; now piney-gen's `placement::sound`, into the build);
- the towns' static models (`statics::inf`, then `tools/statics.py`; now `placement::statics`).

Each generator takes `--volume`, and each `Tables` has a `volume` field,
but only `INF` has been generated.

**The tools can already reach the other executables.** MUT, OUT and QUA
are stripped. The symbol transfer (`tools/xfer.py`, now `piney-gen syms`)
carried about 8,000 Infection names onto each
(`work/<volume>/disc/SLUS_*.syms`, [volumes](../docs/disc/volumes.md)).
`tools/image.py` loads those names, so the rest of the tools read the
stripped executables by Infection's names.

`tools/tables.py` decodes any global through its DWARF type (Infection has
full DWARF). The Python models of the area generator, dungeons, fields,
battle, text, events and saves were checked on all four volumes' own code
([volumes](../docs/disc/volumes.md#systems-across-volumes)).

**A change of rule.** `piney_event::official` says "nothing of either is
kept in this repository". Under this plan the scripts, messages and
strings are kept in the repository as generated data. The repository then
holds game content and should stay private.

## Detecting the volume

`piney_data::volume::Volume { Inf, Mut, Out, Qua }` (built).

The volume is detected from `DATA/GCMN.PRG`, a file the port reads anyway:

| | INF | MUT | OUT | QUA |
| --- | ---: | ---: | ---: | ---: |
| `GCMN.PRG` bytes | 3,121,280 | 3,322,624 | 3,335,680 | 3,377,280 |

- The four sizes differ. A hash of the file confirms the match, so a
  patched or hacked disc is not taken for a known one.
- `SYSTEM.CNF`'s `BOOT2` line is used as a cross-check in tests only.
- A disc that matches none of the four is refused, with a message naming
  the four.

## Where the data lives

In piney-data, beside the tables already generated there. Each system
keeps its row types in its module and one generated file per volume:

```
crates/piney-data/src/
  volume.rs               Volume and its detection
  <system>/mod.rs         the row types and what acts on them
  <system>/inf.rs         generated, one per volume
  <system>/mut_.rs
  <system>/out.rs
  <system>/qua.rs
  <system>/shared.rs      what two or more volumes hold alike, written once
```

Generated Rust only: no data files of the port's own format, no raw dumps
beside the source. Bulk content the game keeps on the disc (textures,
models, streams, sound banks) is read from the disc's `DATA.BIN`, PRGs and
archives at run time, as now. The executable is never read at run time, in
any form: not the file, and not a copy of its memory built into the port.

`dungeon`, `field`, `statics` and `sound` have this shape for all four
volumes; the voices are `tables::voice`, generated by piney-gen (see "The
sound across volumes"). A system reached from several crates (the battle's tables,
the desktop's) still gets its data here, and the crate that acts on it
reads it through piney-data.

**What goes in:** everything read from the executable today.

- The event scripts and message tables. While `plans/event-scripts.md` is
  unbuilt they are generated as the `short` arrays and `{emode, name,
  text}` records `official` reads now. Its source format can later replace
  them.
- The area words, `eventAreaInfo`, `dungeonData` and `volumeNum`.
- The save's initial strings, the story's strings (`serverStr`,
  `getItemMenuStr`, `charTbl`'s names) and the stream tables and subtitles.
- The tables in main that the desktop, top page, title, field UI and
  battle read (skills, items, enemies, the navigator's, the party's chat,
  the menus' help and element data).
- The two bitmap fonts in main that the code uses: `ef12x20` (13,440
  bytes) and `ef8x16` (7,168). They are identical on all four discs, so
  one copy. The four kanji sheets are not used by Infection's code.
- The existing generated tables (dungeon, field, sound, statics) stay
  where they are and gain the other volumes' files.

**Tables in the overlays** are generated too. Most of them point into
main: the desktop's, the field UI's and the battle's menus hold `char *`s
into the executable's strings. Reading them from the PRG at run time would
still need main. The generator resolves each pointer to the text or the
row it names.

A table may stay a run-time PRG read only when nothing in it points out of
its PRG. Its address then comes from the volume's generated layout in
piney-data, not a constant in the reader.

**Addresses in the port.** Every run-time use of an address constant goes
away: it becomes a field of a generated table. The `INF <file>:0x...`
citations in comments stay. They are documentation, and the code audit
below reads them.

## The generator

`piney-gen` (`crates/piney-gen`), a Rust tool the port never runs. Its
manifest is `src/manifest.rs`. It was first written in Python
(`tools/static.py`, 2026-09-26) and moved to Rust the next day, with
byte-identical output:

- `piney-gen gen [--group G]` writes `crates/piney-data/src/tables`;
- `--check` fails on any difference;
- `piney-gen show GROUP --volume V` prints what a group reads.

A group is one module. Each entry names a Rust field, Infection's address,
the overlay loaded when the game reads it, and a layout. For each volume
the entry is found where that volume keeps it:

- on Infection at its own address;
- on the later volumes through the carry (`piney-gen carry`), a finding
  aid that never reaches the port;
- by a custom function where the carry cannot find it, such as a table a
  static initializer fills, run in `piney-eemu`.

What is found is checked against the layout (a string pointer must point
at text), so a wrong place fails in the generator, not in the game.

What the modules hold, and the rules they follow:

- **The game's own types.** A row is a struct built from Infection's DWARF
  (`ty("ccSpcParamData", ..)`): its members by their own names
  (`battle_ability`, `max_hp`), numbers as numbers, floats as plain
  decimals, fixed arrays as `[T; n]`. A keyword is renamed (`type` is
  `kind`). Each such struct has a `write` that lays it into the game's
  memory, for the save.
- **Text as text.** Strings are Rust `&str`, decoded from the game's
  Shift-JIS and checked to encode back byte for byte;
  `tables::sjis::encode` gives the bytes the renderer draws. There are no
  terminators and no escapes. The game's fixed-width menu strings are
  their words (`Slots`).
- **The World's fixed sets are enums.** A table by server or town is a
  method on `piney_data::world::Server` or `Town`
  (`Server::Delta.symbol()`), not a slice indexed by number.
- **Written once.** A value the four volumes hold alike is a plain module
  item (`title::YES`). Only what differs is in the group's struct, one
  static per distinct volume, behind `of(volume)`. A whole row or entry
  that some volumes share is written once and named by its place
  (`NPC_TRADE_45`); smaller parts stay inline.
- **No blobs.** Raw bytes only for opaque bulk (the font bitmaps). A
  list's trailing empty slots are left out (`fixed_empty`) and the
  reader fills them back.

The groups so far:

- `title`, `fonts`, `loaddisp`, `newgame`, `dtmenu`: everything the title
  reads;
- `desktop`, `mail`, `kanji`, `staffroll`, `nameentry`: everything the
  desktop reads;
- `toppage`, `game`: the top page's board, `ccGame`'s own;
- `fieldui`, `battle`, `party_chat`: the field's menus, the battle's
  parameters, the party's chat lines;
- `talk`: every talk record and pointer table the people's lines reach,
  by the address the volume keeps it at (the save holds those addresses).

Where two screens hold the same words in their own places, one table
serves both once the generator's output shows them equal on all four
discs. The desktop's Data screen draws the title's words (`title::YES`):
savedata.cpp's own `STR_` pointers hold the same text on every disc.

## Code that differs between volumes

The port transcribes the game's functions, and the later volumes changed
some of them. One audit finds them all.

`tools/voldiff.py ported` does it:

- It harvests every function the port names: the docs' `covers` and the
  crates' citations (`gcmn 0x0059ddd0`), where the address starts a
  function.
- It carries each to MUT, OUT and QUA through the `.syms`.
- It sorts each into four kinds: *same* (the masked body is Infection's),
  *recompiled* (the opcode sequence is, or the callees in order and the
  constants are), *changed*, or *missing*.

Outbreak's and Quarantine's compiler differs from Infection's. It lays
the stack out anew, fills delay slots, inlines `sqrtf`, `fptosi` and
`fptoui`, and zero-extends by load rather than mask; the structures'
fields also moved. So "recompiled" asks for the same callees in the same
order (a name the carry missed matches any) and the same constants:
compares, masks, loads from `$zero`. An `addiu` from another register is
left out, since it adds a field offset as often as a number.

On 2026-09-26 it found 2,138 functions:

| volume | same | recompiled | changed | missing |
| --- | ---: | ---: | ---: | ---: |
| MUT | 1,539 | 292 | 296 | 11 |
| OUT | 218 | 1,298 | 561 | 61 |
| QUA | 218 | 1,275 | 565 | 80 |

By page, Mutation's changes fall on the battle (82), the field UI (64),
the field game (24), the sound and the dungeons (16 each). Some of
Outbreak's and Quarantine's "changed" menus call nothing Infection's do.
They are more likely names the carry put on the wrong function than
changes.

"Same" and "recompiled" functions need nothing. Each "changed" one is
read and handled in one of two ways:

1. **As data.** The change is a constant or a table (the protected areas,
   the floor counts, the row counts), so it becomes a field of that
   volume's generated data. This is the preferred way: the code stays one.
2. **As a code path.** A new rule, instruction or class, keyed on the
   volume at the narrowest point.

The changes already known ([volumes](../docs/disc/volumes.md#systems-across-volumes)):

- the area generator: areas 71 and 47 become substitute records, and the
  keyword and story-area tables are edited;
- the dungeons: the floor count becomes a field, 90 dungeons are
  hand-made, and the type rule reads a new save bit;
- the fields: `sqrt.s` in OUT and QUA, and area 100 unprotected;
- the battle: the Exdefense rule, 21 party members, rebalanced tables;
- the text: `ccKanjiStrlen` counts every `%x` in OUT and QUA;
- the events: opcodes 168 and 169, and a new operand for 99; the boot's
  `ccStartEvent(volumeNum, 0)`, and `ccThEvent`'s pass walking the disc's
  own main story before the side story of its number (handled, 0209);
- the saves: a 0x854-byte extension, and the carry-over (`ConvGame`).

Then the new code listed under "After Infection" in `GAPS.md`.

## The sound across volumes

The sound's banks and sequences (`commseTbl`, the SQ_LOAD and SQTBL
tables, the play types, `seData`, `bgmWavTbl`, `bgmParam`, the jukebox)
carry by name. piney-gen's `placement::sound` (once `tools/sound_tables.py
gen`) reads them for all four volumes and `sound::tables_of` picks them; `SndData::read` places the
disc's banks with its own volume's tables. Before this the audio placed
every disc's `SNDDATA.BIN` with Infection's tables. That failed on the
later discs, so they had no sound at all.

A carried name keeps Infection's size, and several tables grew:

- the town's banks, from 10 rows to 12;
- the event's banks, from 123 to 127;
- `seData`, from 237 to 259;
- the BGM tracks, from 2 to 8.

A table's rows on a later volume therefore come from its own layout. The
gap to the next global grows by the table's growth when the neighbour is
the same global. Otherwise the table runs to the next global, or keeps
Infection's size where that neighbour has no name. Every bank of the
three later discs then parses, and every BGM track and jukebox row lands
(`tests/sound.rs`, `later_volumes_tables_place_their_discs`).

The voices are piney-gen's `voice` group, read from each volume's own
code, because the code that picks them changed:

- **The event voice.** `ccEvVoiceRequest`'s tables by `event / 100`, from
  its table builds and `voiceFile` stores (done, worklog 226).
- **The field voices.** `ccVoiceRequest`'s cases, case by case from the
  code, and `ccVoicePgFood`'s table. From Mutation on, some English party
  lines play from `MIAE.BIN` while `talkNum[1]` is set (done, worklog 227).
- **The skill words.** `spcVoiceData` and `voiceData` by `charTbl` row, to
  the file list's NULL (done, worklog 227). Mutation's `voiceData` has 21
  rows and 18 files. Outbreak and Quarantine list 21 files, and their
  English tables for 18-20 are still to be checked.
- `setbl.cpp` (the animation notes' sounds, piney-audio's `setbl`) is
  each volume's own (done). Mutation's rows are Infection's, laid out the
  same. Outbreak and Quarantine changed them, and `spcSeTbl` holds 21
  tables there (ids 18-20). `spc0SeData` carried no name there;
  `spcSeTbl[0]` points at it. The readers (`ccSeSetParamSPC` and the rest)
  changed size, but only in code layout.

## Saves

- Each volume has its own card files and the port keeps them apart. Not
  yet: the port's card uses Infection's directory (`mcDirName[0]`,
  `BASLUS-20267DOTHACK`) and slot size on every disc. `ccSaveSys` itself
  now takes the disc's volume, for its messages and for which clear data
  counts.
- A later volume starts either new or from the previous volume's clear
  data (`ConvGame`), as the title offers it.
- The save's extension for the three new characters is read and written
  only on the volumes that have it.

## Checks

- **No executable at run time.** In tests, the ISO reader panics on any
  path matching `SLUS_*`. Every boot and story test runs under it.
- **Equivalence before removal.** For Infection, each generated table is
  compared once with what the run-time read returns today. The old read is
  then deleted. The Infection suite passes unchanged.
- **The generator's check.** `piney-gen gen --check` for all four volumes
  runs with the docs' and worklog's checks before a commit.
- **Boot per volume.** Power on, the title, new game, the desktop, the top
  page and the Root Town. MUT's, OUT's and QUA's tests are ignored until
  they pass. They then join the suite.
- **The audit's table.** `tools/voldiff.py ported` lists no "changed"
  function without a note in the port saying how it is handled (not yet:
  the counts are under "Code that differs between volumes").

## Plan

1. **Phase 0.** `Volume` and its detection (done), and the driver running
   the existing generators. Each system's `Tables` is picked by the
   detected volume.
2. **Phase 1: Infection off the executable - a shortcut, removed.** Done
   the short way first, and removed on 2026-09-26 (below): `tools/main_data.py` writes each volume's main data (from the
   font `ef12x20` to the end of main, the .bss reading zero) and the three
   function bodies the port decodes (`ccCheckVoiceGrp`, `ccParticle::Setup`,
   `ccGetItemIcon`) to `piney-data/src/main_data/<volume>.bin`, about
   550 KB each, and `Image::main(volume)` stands where `Image::elf` of
   the executable stood. Every reader works unchanged, and the game calls
   `iso::deny_executable()` at start so a missed one fails loudly. The
   event scripts and the area words are already typed tables; the other
   readers still read by Infection's addresses, now into the generated
   bytes. They become typed tables system by system as each is made
   right for the other volumes (phase 2), which is also where their
   addresses stop being Infection's.
3. **Phase 2: the other volumes' data.** Generated for MUT, OUT and QUA,
   with the carry's misses resolved in the manifest.

   A first step (worklog 199): `tools/main_data.py` also writes each later
   volume's *carry*. That is where Infection's globals and functions sit in
   the volume: by the names the symbol transfer carried, unique on both
   sides; by what the paired functions build, for names that repeat
   (string literals); and the fonts by content. `Image::at(inf_va)` moves a
   reader's Infection constant into the disc's volume, and is the identity
   on Infection. Only constants go through it: a pointer read from the
   image is already the volume's. `PINEY_CARRY_TRACE` names the addresses
   nothing carries. A reader whose table kept its layout works on every
   volume once its constants go through `at`. One whose table changed (21
   `charTbl` rows, a table filled by a static initializer the port ran on
   Infection) still needs that volume's own reading. The game
   starts a later disc with a warning (at first only with
   `PINEY_TRY_VOLUME=1`), to find the next reader the boot needs.

   Done so far (worklog 200):
   - The save's extension and the later volumes' `Init` and `NewGame`,
     checked against each volume's own code.
   - Tables a static initializer fills, run per volume (`saveSysMsg`;
     now `piney-gen`'s `sinit`).
   - The title's scene by volume.
   - The direct reads of an Infection constant through `at` (218, done
     mechanically).
   Then (worklogs 201-202): the title's per-volume menus; the carry
   improved:
   - votes at a global's start outrank those into it;
   - the code outranks a wrong name (Mutation's `skillTbl`);
   - an overlay's copy of a main global is keyed by the overlay;
   - globals found once by their bytes;
   - equally spaced neighbours interpolated.
   All Image readers' constants and literals now go through `at`.
   Mutation boots through New Game into the desktop's setup; its opening
   streams play.

   Then (worklogs 203-204):
   - each volume's own sound tables;
   - a pointer pass in the carry (globals of string pointers, such as
     the name entry's `STR_INFO_MSG`, which only an unnamed `__sinit`
     builds);
   - the mail's reply links per volume, run from each volume's own
     `__sinit_mailtbl.cpp` (`sinit::mail_links`: 375 mails and 364
     replies from Mutation on);
   - the stream archives in their type order (`STRSUB` is type 5);
   - Outbreak's and Quarantine's `tmp.ccs` members;
   - the readers that bound a constant before reading it (`let at =
     NPC_TBL + ...`), and helpers handed one, which the first sweeps
     missed.
   All three later discs now boot through New Game into their desktops,
   with their own mail.

   The carry misses are listed offline by checking every address the
   source names against each volume's carry: 7 for Mutation, 29 for
   Outbreak and 28 for Quarantine. Mutation's 7 are each referenced by
   one function that Mutation changed (`ccGame::ChangeScene`,
   `ccEvent::Execute`, `InitSpcParam`, `ConvergenceSystem`), so they
   need finders where their systems are ported.
   **The shortcut removed (2026-09-26).** The embedded main data and the
   carry kept every reader walking executable memory by Infection's
   addresses: the executable read at run time in all but name, and the
   later volumes run as Infection with its addresses moved. They are gone
   from the crate: `Image::main`, `Image::at` and the `main_data` files.
   Each system is rebuilt as "The generator" says: typed tables per
   volume, written once where volumes agree, readers taking tables rather
   than addresses. Until a system is rebuilt its readers find nothing, on
   Infection too. The carry's passes stay in the generator
   (`piney-gen carry`), which uses them to find a volume's globals;
   nothing of them reaches the port. The order of the rebuild:
   what the boot reaches first (the title, the save, the desktop, the top
   page), then the field UI, the world, the battle, the effects and the
   streams.
4. **Phase 3: the audit.** The changed functions handled as data or as
   code paths.
5. **Phase 4: booting.** Each volume boots to its Root Town, then works
   through "After Infection" in `GAPS.md`: the new instructions, towns,
   areas, bosses and the party of 21.

Infection's own work (its unknowns, its side events) goes on beside these
phases. Phase 1 changes where Infection's data comes from, not what it is.

## Open questions

- **The size in git.** Measured: the scripts 2.7 MB of text (four
  volumes), the main data 2.2 MB of bytes, the generated tables about
  1.5 MB of Rust. The main data shrinks as the typed tables replace it.
- **The fragment disc.** It shares the engine's baseline with Quarantine,
  but it is set aside for now.
- **Run-time PRG reads.** Whether any table stays one, or every overlay
  table is generated so that the PRGs are read only for their bulk (if
  they have any the port needs).
